# Context Mesh Framework

## Overview

Context Mesh keeps durable project context close to the code. Work follows three
connected phases: **Intent → Build → Learn**.

1. **Intent** records the user or business outcome and the decisions that guide
   it before implementation.
2. **Build** implements the approved work while following the recorded decisions
   and reusable patterns.
3. **Learn** captures outcomes, changes, and significant lessons after the work.

## File Type Separation

Keep each concern in exactly the appropriate file type.

| File type | Purpose | Must not contain |
| --- | --- | --- |
| `intent/feature-*.md` | What a capability does, why it matters, and functional acceptance criteria | Technical design, library names, source paths, or code examples |
| `decisions/*.md` | Technical choices, rationale, alternatives, and outcomes | Business requirements or implementation tutorials |
| `knowledge/patterns/*.md` | Reusable implementation guidance and code examples | Feature requirements or unexplained architecture decisions |
| `knowledge/anti-patterns/*.md` | Approaches to avoid and safer alternatives | General feature intent |
| `agents/*.md` | Scoped instructions for agents or roles | A substitute for feature, decision, or pattern records |
| `evolution/*.md` | Changelog entries and learning records | Undocumented implementation plans |

Feature files may link to the decisions and patterns that support them, but must
not duplicate their technical content.

## Plan, Approve, Execute

This is mandatory for new work:

1. **Plan**: document or update the relevant feature intent and any required
   decisions before coding.
2. **Approve**: obtain the required human approval for the proposed scope and
   decisions before implementation.
3. **Execute**: implement the approved work, follow documented patterns, run
   appropriate validation, and update context with the result.

Documentation of an already-existing codebase is an Intent capture activity:
record facts and clearly mark inferences rather than retroactively claiming an
unrecorded approval.

## When to Create Files

Create a feature file when a distinct user-facing capability or business outcome
exists. Create a decision when a technical choice materially constrains future
work. Create a pattern when code structure, conventions, or an implementation
technique are reusable. Create a learning record when an outcome changes an
assumption or provides a reusable insight.

Do not create a file for a tiny implementation detail, an isolated one-off with
no future value, or information already fully and accurately represented in an
existing context file. Update that file instead.

## Context Structure

```text
context/
├── .context-mesh-framework.md
├── intent/                 # Project and feature intent
├── decisions/              # Technical decisions
├── knowledge/
│   ├── patterns/           # Reusable implementation patterns
│   └── anti-patterns/      # Practices to avoid
├── agents/                 # Agent-specific guidance
└── evolution/              # Changelog and learning records
```

## Bidirectional Links

Use relative Markdown links. A feature links to every directly relevant decision
and pattern. Each linked decision links back to affected features; each pattern
links back to its related feature and decision. Keep these links current whenever
files are added, renamed, or removed.

## Status Requirements

Every feature, decision, and pattern must have a `Status` section with its
creation date and current status. Existing-code documentation must say when a
conclusion was inferred rather than explicitly documented. Decisions also record
outcomes as the project evolves.

## Definition of Done

Before declaring implementation complete:

- [ ] Feature intent and acceptance criteria are current.
- [ ] Required decisions exist and have been approved.
- [ ] Code follows applicable documented patterns.
- [ ] Appropriate tests and validation pass.
- [ ] Context links and status sections are current.
- [ ] The evolution changelog records the change.
