# Decision: SonarQube Analysis Configuration

## Context

The repository publishes SonarQube quality and coverage badges and already has
a scan workflow, but it lacked the root project descriptor that binds a scan to
its project identity, source roots, test roots, coverage report, and quality
gate behavior.

## Decision

Use `sonar-project.properties` in the repository root with project key
`ha-reminder`, source code in `custom_components/ha_reminder`, tests in
`tests`, and the `coverage.xml` report generated by pytest. Configure the scan
to wait for the SonarQube quality gate. The GitHub Actions workflow runs on
Python 3.13, matching the supported project runtime, and uses the repository's
established public SonarQube endpoint with a `SONAR_TOKEN` secret.

## Rationale

The existing README badges establish `ha-reminder` as the registered SonarQube
project key. Keeping analysis settings in a versioned root descriptor makes
local and CI scans consistent without storing credentials in source control.
The public endpoint remains explicit because the repository validation convention
requires it. The coverage report reflects meaningful test execution and does not
exclude production logic.

## Alternatives Considered

- Keep project metadata only in the GitHub workflow: rejected because local
  scans would have no stable project identity or source/coverage configuration.
- Move the public SonarQube URL to a repository variable: rejected because the
  repository's integration validation requires the established endpoint marker
  in the workflow.
- Exclude production modules to increase coverage: rejected because coverage
  must measure the integration's real production code.

## Outcomes

The workflow produces `coverage.xml` before the scan. Repository administrators
must provide `SONAR_TOKEN` as a GitHub Actions repository secret; the configured
SonarQube quality gate enforces coverage thresholds.
